# ADR-002: PostgresDatabase and attached policies for shared databases

- **Status:** Proposed (draft)
- **Date:** 2026-11-05
- **Deciders:** pgroles maintainers
- **Supersedes / superseded by:** —

## Context and constraints

Several teams sharing one PostgreSQL database is a common setup, and pgroles
has two partial answers for it, neither of which holds up between teams that
do not fully trust each other.

**Operator: several `PostgresPolicy` resources on one database.**

- Every policy carries its own `connection`, so every team holds a credential
  for an executor with `CREATEROLE`. Any team can bypass pgroles entirely.
- Policies are compared through `ownership_claims`
  (`crates/pgroles-operator/src/crd.rs`), which claims every role a policy
  mentions, including grantees and membership members. Two teams adding the
  same person to their own team roles conflict.
- A conflict blocks *both* policies, so a new or careless policy can freeze one
  that was converging.
- Until #263, "the same database" meant the same namespace and Secret, so
  policies reaching one database through different Secrets were never
  compared. #263 resolves the target on the server, but cannot see across
  separate operator installs, and leaves a window of one apply.

**CLI: bundles.** Ownership is tracked per grant, membership and default
privilege, which is the right granularity. But scope is self-declared, and
#262 shows that memberships, grantees and database grants are not bounded by
it at all: a fragment can add itself to another fragment's `CREATEROLE` role.

Constraints in force:

- **No pgroles state in the database.** The maintainers prefer that pgroles
  keeps nothing beside the roles and grants it manages, which rules out a
  claims table in PostgreSQL.
- **Pre-1.0.** Breaking changes are acceptable when they buy a better
  long-term API (as in ADR-001).
- **Prior art:** Kubernetes Gateway API replaced `Ingress` with resources
  split by owner (`Gateway` for the platform team, `HTTPRoute` for application
  teams), attachment that the parent's owner controls (`allowedRoutes`,
  `ReferenceGrant`), conflict resolution by precedence instead of mutual
  blocking, and status reported per parent. `PostgresPolicy` today is where
  `Ingress` was.

## Decision 1 — A `PostgresDatabase` kind; team policies attach to it

`PostgresDatabase` is owned by whoever owns the database. It holds the
connection, execution settings (`mode`, `approval`, `interval`,
`reconciliationMode`), shared `profiles` and `rolePattern`, and
`delegations`.

A `PostgresPolicy` sets `databaseRef` instead of `connection`:

```yaml
apiVersion: pgroles.io/v1alpha1
kind: PostgresPolicy
metadata: {name: billing, namespace: billing}
spec:
  databaseRef: {name: appdb, namespace: platform}
  roles:
    - name: billing_api
      login: true
  schemas:
    - name: billing
      owner: billing_migrator
```

Consequences:

- "The same database" is an object reference, not a Secret name or a value
  inferred from the server.
- Only the database owner's namespace holds a database credential.
- A policy with `connection` keeps working as a single-owner policy, the way
  `Ingress` was never removed.

*Considered:* a new kind for team policies (as Gateway API added `HTTPRoute`).
Rejected for now: the content schema is identical, and a second kind would
duplicate it. Revisit if attached and standalone policies diverge.

## Decision 2 — Scope comes from the database owner's delegation

```yaml
spec:
  delegations:
    - namespaces: [billing]
      roles: ["billing_*"]
      schemas: [{name: billing, facets: [owner, bindings]}]
```

A policy's scope is derived from the delegations that name its namespace,
never from anything the policy says about itself. The rules, implemented in
`pgroles-core` (`attachment.rs`) so the CLI can share them:

- Every role the policy **creates** must match a delegated pattern. That
  includes roles generated by schema bindings; otherwise a `role_pattern` such
  as `team_{profile}` mints names inside another team's delegation.
- Schema `owner` and `bindings` facets, and grants or default privileges on a
  schema, need that facet delegated.
- **Membership** in a role needs the role to be created by the same policy.
- **Database-level grants** (which name no schema) need the grantee to be
  created by the same policy. `PUBLIC` stays with the database owner.
- Granting on what a policy owns **to any role** is allowed: `billing` may
  grant `SELECT` on its tables to the platform-owned `team_payments`, and
  `REFERENCES` to `shipping_migrator`.

This is the design #262 asks for, with one difference: scope is granted by
the database owner instead of being self-declared and then policed.

## Decision 3 — Oldest policy wins; a rejected edit keeps its last accepted content

Attached policies are composed in `creationTimestamp` order, then by
namespace and name. A policy that collides with an older one is rejected
alone (`Accepted=False`, reason `Conflicted`), and the rest still converge.

Precedence alone is not enough. The prototype found a takeover: a squatting
policy that redefined `billing_api` with `superuser: true` was correctly
rejected as `Conflicted`. When billing later pushed an out-of-scope edit, the
squatter became the oldest claimant and was accepted, and the composed plan
contained `ALTER ROLE "billing_api" SUPERUSER`. Only the executor not being a
superuser stopped it.

So a rejected generation does not withdraw the policy: its last accepted
content stays composed (`Retained`), keeping its claims and its applied state,
the way a Deployment keeps its old ReplicaSet when a rollout fails. The
database status records `servingGeneration` and the content of that
generation for each attached policy.

## Decision 4 — One composed plan per database

The controller composes every accepted policy into one operator-owned
`PostgresPolicy` (`<database>-composed`, labelled `pgroles.io/composed-for`).
The existing policy reconciler plans and applies it, so locking, plans,
approval, authority preflight and drift handling are reused unchanged. One
database has one inspect/diff/apply cycle, which removes races between
policies on that database (the window #263 documents).

*Considered:* teaching the policy reconciler to compose directly. That is
cleaner long term (no generated object in the user's view), but touches every
path in a 6,500-line reconciler. The generated policy is the cheaper first
step and can be folded in later without an API change.

## Decision 5 — The executor belongs to the database owner

`spec.executorRole` names the role the connection authenticates as. The
composed policy declares that role's inherited membership in every role that
owns a schema or default privileges.

Without this, the prototype failed in `authoritative` mode. After the first
apply the executor held only its `ADMIN` edge on the roles it created, not the
`INHERIT` membership `createrole_self_grant` adds. Undeclared memberships are
revoked like any other (`executor-privileges.md`), and no attached policy
declares the executor. Grants on objects those roles own then failed authority
preflight. Teams should not need to know the executor's name.

## Decision 6 — Status per attached policy and per database

- Each attached policy gets `Accepted` (with the rejection reason) and a
  `Ready` mirrored from the composed policy.
- `Ready` and `observed_generation` on an attached policy describe its current
  generation only once the composed policy has reconciled the composition that
  included it. Mirroring the composed policy's `Ready` naively reported a
  newly attached policy ready before its content was applied.
- `PostgresDatabase.status.attached` lists every attached policy in precedence
  order, so the database owner sees all teams without listing namespaces.

## Prototype evidence

A prototype implements decisions 1 to 6 (local branch
`prototype/postgres-database`, not yet published). It ran against a real
`kube-apiserver` 1.31 and PostgreSQL 16, with a non-superuser `CREATEROLE`
executor. The teams are `examples/microservices` (platform, billing,
shipping), turned into attached policies, plus deliberately bad policies. All
27 checks pass:

| Scenario | Result |
|---|---|
| Three teams bootstrap, migrate, then attach full policies | Converge as one plan; cross-team grants work (billing grants `REFERENCES` to `shipping_migrator`, `SELECT` to `team_payments`) |
| Isolation | `billing_api` cannot read `shipping.shipments`; `billing_worker` cannot insert |
| Membership into another team's role | `OutOfScope`; nothing reaches PostgreSQL |
| Namespace without a delegation | `NotDelegated` |
| `CREATE` on the database to `PUBLIC` | `OutOfScope` |
| A newer policy redefining `billing_api` as superuser | `Conflicted`; the older policy and the database stay `Ready` |
| Out-of-scope edit to an accepted policy, squatter waiting | Edit rejected, previous generation still applied, squatter still `Conflicted`, `billing_api` not superuser |
| Credentials | Only the database owner's namespace holds a database Secret |

Moving the example to delegations needed one change: database `CONNECT` for
the platform-owned `team_*` roles moved from the billing and shipping policies
into the platform policy.

Findings that are not decided here:

- **A team leaving.** Deleting shipping's policy left its roles in place
  (nothing drops them), and billing's remaining grant to `shipping_migrator`
  never converges: the role is no longer declared, so its privileges are not
  inspected. Cross-team grantees should probably be treated as external roles
  of the composition, with a reported "dangling reference" when no policy
  creates them.
- **Owner self-grants.** `GRANT CREATE, USAGE ON SCHEMA billing TO
  billing_migrator`, where `billing_migrator` owns the schema, is accepted but
  never shows in the ACL when run by a non-superuser executor, so the plan
  never converges. This is a pre-existing issue, independent of this design.

## Alternatives considered

- **Claims stored in the database** (a table updated under the advisory
  lock). Atomic and visible to every operator install and the CLI, but puts
  pgroles state beside the roles. Rejected by the constraint above.
- **Server-resolved identity only (#263).** Correct for inline-connection
  policies and kept for them, but it cannot remove the executor credential
  from teams, decide precedence before connecting, or bound scope.
- **Block both policies on conflict** (current behaviour). Lets any
  newcomer freeze an established policy.
- **Self-declared scope with stricter checks (#262 alone).** Fixes escalation
  inside a bundle, but scope remains whatever the fragment says, which is not
  a boundary between teams.
- **Admission webhook.** Cannot know which database a policy reaches without
  connecting, so it falls back to comparing Secret names.

## Open questions

1. **Approval.** The database owner approves composed plans. Should teams
   approve the part of a plan their policy causes, and how would that bind to
   one plan digest?
2. **Generated passwords.** The composed policy lives in the owner's
   namespace, so generated password Secrets land there, where the team cannot
   read them. They should be written to the attached policy's namespace.
3. **Leaving.** Should deleting an attached policy retire its roles
   (finalizer and retirement plan), orphan them, or require an explicit
   `retirements` entry first?
4. **Cross-team references.** Implicit externals, dangling-reference status,
   and whether the referenced team must consent (a `ReferenceGrant`
   equivalent).
5. **Delegation selectors.** Namespace names only, or label selectors as in
   `allowedRoutes`?
6. **Retained content.** Where the last accepted content lives: in
   `PostgresDatabase` status (bounded by object size), or elsewhere.
7. **Candidates and ephemeral access.** How `PostgresPolicyCandidate` and
   `EphemeralAccessPolicy` refer to attached policies.
8. **CLI parity.** A bundle root is close to a `PostgresDatabase`; the
   attachment rules should apply to bundles behind an opt-in, then by
   default (#262).
9. **Migration.** A `pgroles migrate` that generates a `PostgresDatabase` and
   attached policies from existing inline-connection policies.

## Consequences

- Teams no longer hold executor credentials; the database owner does.
- Conflicts resolve per policy, and a broken edit stops only that edit.
- Every policy on a shared database becomes one plan, so a slow or blocked
  composed plan affects every team on it. Mitigations (per-team approval,
  isolating failing statements) are open questions, not solved here.
- The operator gains a kind, a controller, and a generated policy users will
  see in listings.
